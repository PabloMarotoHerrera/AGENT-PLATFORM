## 8. TaskGraphPattern

TaskGraphPattern decomposes an objective into graph nodes and dependencies. Task nodes are work units. Edges represent dependency, blocker, evidence, review, integration, or handoff relationships. The task graph is internal topology, not a manual lane list. Manual work packets are projections of task graph nodes.

| Aspect | Definition |
| --- | --- |
| strengths | Makes dependencies, blockers, review paths, and integration points explicit. |
| limitations | Can become too rigid or too large without recursion stop rules. |
| required P7 objects | TaskGraphRef, TaskGraphNode, TaskGraphEdge, ManualExecutionProjection. |
| manual projection rule | Project selected graph nodes into human-run tickets. |
| blocked runtime interpretation | No automatic planning, scheduling, or dispatch. |

## 9. BlackboardPattern

BlackboardPattern defines a shared working memory space for partial results, evidence, contradictions, blockers, and unresolved questions. The blackboard is conceptual metadata space, not persistence runtime. It is useful for integration, reviewer mesh, conflict resolution, and cross-agent visibility. Memory manifest can later reference blackboard slices manually.

| Aspect | Definition |
| --- | --- |
| strengths | Improves cross-lane visibility and contradiction handling. |
| limitations | Requires careful freshness and authority markers. |
| required P7 objects | BlackboardRef, BlackboardFinding, BlackboardMemoryRef, EvidenceConflictMarker. |
| manual projection rule | Include blackboard slices in manual context packs and integrator prompts. |
| blocked runtime interpretation | No persistence DB, event bus, graph DB, or live shared store. |

ContractNetPattern allocates work by task advertisement, capability fit, bid/claim, selection, and acceptance. It is useful for future dynamic routing. In P7 manual mode, the lead agent manually simulates allocation by assigning work packets to lanes/harnesses. No automatic auction and no autonomous claiming are approved.

| Aspect | Definition |
| --- | --- |

| limitations | Can create overhead for small tasks. |
| required P7 objects | CapabilityCellRef, RoutingDecisionRef, ManualExecutionProjection. |

| blocked runtime interpretation | No autonomous market, bidding, or claiming. |

## 12. ImmuneReviewPattern

ImmuneReviewPattern models a review mesh inspired by immune detection: anomaly detection, contradiction detection, boundary enforcement, quarantine recommendations, and rework loops. It is useful for security, validation, consistency, context drift, product boundary, external boundary, and evidence conflicts. Reviewer agents are not just human roles; they can be modeled as immune safeguards around outputs and routes. No automatic quarantine or rejection is approved.

| Aspect | Definition |
| --- | --- |
| strengths | Converts review into systemic safeguards. |
| limitations | Risk of excessive rework and false positives. |
| required P7 objects | ReviewerMeshRef, ImmuneReviewMarker, HumanDecisionPoint. |
| manual projection rule | Use manual reviewer prompts and explicit quarantine recommendations. |
| blocked runtime interpretation | No auto-review, automatic quarantine, or automatic rejection. |

They may inform clarity, decision rights, escalation, review discipline, and operational cadence. They must not dominate the agent-native architecture and must not create military/human hierarchy as the final model.
